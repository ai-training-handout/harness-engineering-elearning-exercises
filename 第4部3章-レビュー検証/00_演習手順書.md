# 演習ステップ定義：レビュー＆検証ハーネス（第4部3章）

> **「課題指示 → やってみる」の反復で進める。** 第4部2章と同じ設計思想。各ステップの完了条件を自分で確かめてから次へ進むこと。
> 目標時間：**45分**（手を動かす時間。レビューを走らせている間の待ち時間〈1回2〜5分〉は含めない）。ステップごとの想定時間は下表のとおり（合計45分）。時間は目安であり、超えても構わない。
> 詰まったら：完成形リポジトリ（受講ページの第4部3章から `第4部3章_完成形リポジトリ.zip` をダウンロードする。使い方は同梱の `手順.txt`）の `step-N-done` タグで次のステップから再合流できる。

## 0. この演習の構造

- 第4部2章が「**作る**」ハーネスなら、本章は「**測る・止める**」ハーネス。レビュー対象は、**第4部2章で作ったアプリへの機能追加 PR**（検索・絞り込み）。1本のストーリーでつながっている。
- **レビュアーはコードを書き換えない。** 指摘するだけ。これを規約ではなく**権限**で保証する（Step 6）。
- 第4部2章と同じく、各ステップに `step-N-done` のスナップショットがある。

| Step | 内容 | 受講生の作業 | 想定 | スナップショット |
|---|---|---|---:|---|
| 0 | サンプル PR を読む（流し読み） | 確認のみ | 5分 | `step-0-done` |
| 1 | CLAUDE.md：却下基準の正本 | **書く** | 10分 | `step-1-done` |
| 2 | 入力の取得：何を渡すか | 確認＋調整 | 3分 | `step-2-done` |
| 3 | 4観点サブエージェント | **書く** | 10分 | `step-3-done` |
| 4 | aggregator：集約と判定ルール | **書く** | 6分 | `step-4-done` |
| 5 | 1回レビューを回す（R1） | 実行と検証 | 5分（実行待ちを除く） | — |
| 6 | 入力検証 Hook・報告様式・権限 | 雛形を有効化 | 3分 | `step-6/7/8-done` |
| 7 | 走らせ方を3条件で比較する | 実行と考察 | 3分（実行待ちを除く） | — |
| | **合計** | | **45分** | |

> Step 6 は元の3層（UserPromptSubmit Hook／Output Styles／Permissions）をまとめて1ステップにしている。いずれも雛形配布で、受講生が書く量が少ないため。

## Step 0：サンプル PR を読む（5分）

### 課題指示

始める前に、このフォルダを演習用のフォルダにする。公開リポジトリ（`harness-engineering-elearning-exercises`）から取得した場合は、取得した場所の**外へコピーして**、コピー先で Claude Code を起動する（配布物の README「使い方」）。

レビュー対象を自分の目で読む。**これが唯一、人間が先に読む機会**。

- `sample-pr/PR.md` — PR 本文（変更概要・テスト結果）
- `sample-pr/diff/task-search.diff` — 差分（827行）
- `sample-pr/spec-excerpt.md` — 照合する仕様

**PR 本文には「テストは 82 passed で全 green」と書かれている。**

読み終えたら、この演習用フォルダで Claude Code を**対話モードで1回起動**し、「このフォルダを信頼するか」の確認で**信頼を選ぶ**。最初は No, exit が選ばれているので、矢印キーで **Yes, I trust this folder** を選ぶ。第4部2章のフォルダで選んでいても、フォルダが違えばもう一度必要になる。続けて「New MCP server found in this project: github」と出たら、固定サンプルのレビューには使わないので **Continue without using this MCP server**（最初に選ばれている項目）のままでよい。信頼を選んでいないフォルダでは、ヘッドレス実行（`claude -p`。Step 7 の3条件を画面を開かずに回すときなど）が `.claude/settings.json` を読まず、許可した操作でも止まる。

### 完了条件

- この PR が何を実装したものか説明できる
- **「テストが green なら、この PR はマージしてよいか？」**という問いに、まだ答えを出さない（Step 5 で答え合わせをする）
- Claude Code を対話モードで1回起動し、フォルダの信頼を選んだ
- 差分は**流し読みでよい**（どのファイルをどう変えたかが分かれば十分）。中身の精読は Step 5 でハーネスの指摘と突き合わせるときに回す

## Step 1：CLAUDE.md — 却下基準の正本（10分・**書く**）

### 課題指示

**このハーネスで最も重要なステップ。** 「何を Blocker とし、何を Nit とするか」を1箇所に書く。ここがぶれると、レビュー結果が実行のたびに変わる。

`CLAUDE.md`（雛形・空欄あり）を**自分の手で**（エディタで）書く。エージェントに書かせない（`.claude/settings.json` の deny で `CLAUDE.md` の編集を禁じている。レビュアーが自分の基準を書き換えられない設計）。書く内容：

- **重大度の定義**：Blocker / Major / Minor / Nit と、それぞれが判定に与える影響
- **4観点それぞれの基準**：correctness / security / performance / readability
- **correctness には「テストの質」を含める**（形骸テスト・skip 無効化・期待値ハードコード）
- **格上げの禁止**：迷ったら上に寄せる、をしない。指摘がなければ「指摘なし」と書く

### 完了条件

- 4観点それぞれに **Blocker の例**が書かれている
- **readability は原則 Blocker を出さない**と明記されている
- 「指摘をひねり出さない」という趣旨が書かれている

### なぜ却下基準を1箇所に置くのか

**人間のレビューがぶれる最大の原因は、基準が人の頭の中にあること。** 明文化して初めて、自動レビューも人間レビューも同じ物差しになる。

## Step 2：入力の取得 — 何を渡すか（3分）

### 課題指示

レビュアーに何を見せ、何を見せないかを決める。

| 渡す | 渡さない |
|---|---|
| 変更行の diff | リポジトリ全体・変更のないファイル |
| PR 本文・関連 Issue の要約 | Issue のコメント全履歴 |
| 仕様の**該当条項の抜粋** | 仕様書の全文 |

### 完了条件

- 取得方針を読み、**なぜ全文でなく差分なのか**を説明できる（レビューは差分に対して行うもので、差分外の粗探しは仕事ではない）

### 補足（実測でわかったこと・正直に扱う）

当初この層は「**コスト制御の第一手**」と説明する予定だったが、**実測では消費が15%しか変わらなかった**（対象 PR が821行と小さいため）。**渡す範囲を絞る理由は、コストよりも「レビューの焦点を差分に保つこと」にある。** 大きな PR でコストに効くかは未検証。

## Step 3：4観点サブエージェント（10分・**書く**）

### 課題指示

correctness / security / performance / readability の4体を定義する。**各自は自分の観点の基準だけで判断し、他観点の指摘を書かない。**

`.claude/agents/` に次の4ファイルを作る（書式は `.claude/agents/_雛形.md`）。**4ファイルは自分の手で（エディタで）書く。** 配布の `.claude/settings.json` が `.claude/` の編集を deny しているので、Claude Code に書かせると拒否される（Step 1 の `CLAUDE.md` と同じく、レビュアーが自分の基準を書き換えられない設計）。**ファイル名は `/review` Skill がこの名前で呼ぶので変えない**（違う名前だと `/review` が動かない）：

- `correctness-reviewer.md`
- `security-reviewer.md`
- `performance-reviewer.md`
- `readability-reviewer.md`

観点ごとに必ず入れること：

| 観点 | 必須の視点 |
|---|---|
| correctness | 仕様との突き合わせ ＋ **テストの質**（「このテストは、実装をわざと壊したら落ちるか？」） |
| security | 認可の抜け。特に**権限と検索の合成**（絞り込みが権限範囲の外に及んでいないか） |
| performance | **全件ロード後の Python フィルタ**になっていないか（仕様が SQL レベルを要求している） |
| readability | 実害を言えるなら Major、言えないなら **Nit** |

### 完了条件

- 4体の定義があり、それぞれ**「他観点の指摘を書かない」**が明記されている
- correctness の定義に**テストの質**が入っている
- **なぜ観点を分けるのか**を説明できる（観点の混線防止と、自己採点バイアスの排除）

## Step 4：aggregator — 集約と判定ルール（6分・**書く**）

### 課題指示

4観点の所見を1つにまとめ、**マージ可否を機械的に判定する**ルールを書く。ファイルは `.claude/agents/aggregator.md`（書式は `_雛形.md`。この名前も `/review` Skill が固定で呼ぶ）。Step 3 と同じく、**自分の手で（エディタで）書く**（`.claude/` の編集は deny されている）。

| 条件 | 判定 |
|---|---|
| Blocker ≥ 1 | Block |
| Blocker なし・Major ≥ 1 | Request Changes |
| Minor / Nit のみ | Approve |

**あわせて「格上げの検算」を入れる**：readability の指摘が Blocker になっていたら引き下げる。実害のない指摘が Major 以上なら Nit に引き下げる。落とし先は **Nit**（Major で止めない）。観点をまたいで同じ根本原因を指す指摘は1件に統合し、重大度は高い方を採る（統合したことを報告に書く）。

### 完了条件

- 判定ルールが**機械的**（裁量が入らない）
- 格上げの検算が入っている
- **なぜ機械的にするのか**を説明できる（判定が再現しないと、人の判断と突き合わせても、ずれの原因が基準にあるのか判定のぶれにあるのか切り分けられない）

## Step 5：1回レビューを回す（5分・実行と検証。レビューの実行待ちは除く）

### 課題指示

```
/review sample-pr
```

出た結果を、**Step 0 で自分が読んだときの印象と突き合わせる**。

終わったら、Step 7 の比較に使う **R1（並列）の消費トークンを記録する**：

```sh
python3 cost/measure_tokens.py --label "R1 並列"
```

ハーネスが報告の最後に「計測済み」と書いていれば（`/review` Skill の「実行後」がエージェントに測らせる）、同じ実行が二重に記録されるので手では測らない。

### 完了条件

- 判定（Approve / Request Changes / Block）と、その根拠になった指摘を**自分の言葉で**書いた
- 指摘の**件数と観点の内訳**（correctness / security / performance / readability に何件ずつ）を書いた
- Step 0 で自分が出した「マージしてよいか」の答えと、ハーネスの判定を比べた
- 指摘のうち、**自分が Step 0 で読んだときには気づかなかったもの**を挙げた

（答え合わせは、ここまで書いてから、受講ページの第4部3章にある `第4部3章_答え合わせ.pdf` を開く）

## Step 6：入力検証・報告様式・権限（3分・雛形を有効化）

### 課題指示

3つの層をまとめて有効化する。

- **UserPromptSubmit Hook**：レビュー実行**前**に対象（PR 番号・リポジトリ・ブランチ）を検証する
- **Output Styles**：観点/重大度/箇所（file:line）/問題/修正提案 を毎回同じ様式で出す（配布の `settings.json` で `outputStyle: review-report` を指定してある。`/config` の Output style で確認できる）
- **Permissions**：読み取り中心。**編集・push・merge は deny**

### 完了条件

- 対象を指定せずに `/review` を実行すると、**実行前に止まる**ことを確認した
- **レビュアーがコードを書き換えられない**ことを、設定で確認した（`Edit`・`Write` ツールは deny で止まる。`sed -i`・`tee` などシェル経由の書き換えも deny に入れてある。それ以外のシェル書き換えは既定の確認に落ちるので、正確には「黙っては書き換えられない」）

### なぜ実行前に検証するのか

対象を取り違えたまま4観点を並列で回すと、**間違った対象にコストを払う**ことになる。止めるなら実行前。

## Step 7：走らせ方を3条件で比較する（3分・実行と考察。1条件2〜5分の実行待ち×2は除く）

### 課題指示

**まず予想を立ててから**実行する。「4観点を並列でなく逐次にしたら、コストはどうなると思うか？」

```
/review sample-pr --sequential   # 逐次
/review sample-pr --budget       # Blocker 早期打ち切り
```

各実行のあとに計測する：

```sh
python3 cost/measure_tokens.py --label "<条件名>"
python3 cost/measure_tokens.py --report
```

### 完了条件

- 予想と実測を並べ、**差の有無と方向を記録した**（食い違わなくてもよい。予想が当たることもある）
- **単発の測定で結論を出さない理由**を言える
- 「**測らずに最適化していたら、どんな判断ミスをしていたか**」を言える

### この演習の主題

**走らせ方の選択は、実測してからでないと決められない。** 「逐次にすれば安くなるはず」「早期打ち切りなら減るはず」という直感は、測る環境によって当たることも外れることもある。実測で一貫して言えるのは次の3点だけである。

- **並列は速い**（所要時間の差は環境をまたいで安定している）
- **トークンは環境依存で、実行ごとのばらつきも大きい**。単発の計測で方向を決めてはいけない。**分布で見る**
- **早期打ち切りは網羅性を捨てる**。performance・readability の指摘が出ないので、修正が一巡で終わらない

数値そのものより、「**自分の予想がどう外れたか**」と「**測らずに決めていたら何を間違えたか**」を言葉にすることがこのステップの目的である。これは第7部3章「コストと品質・速度のトレードオフ」（コスト最小化ではなく、要求品質を満たす最小コストを狙う）につながる。

## 5. 発展課題（時間が余った受講生／自習用）

**自分のリポジトリの実 PR をレビューさせ、自動判定を自分の判断と突き合わせる**。

```
/review #<PR番号>
```

> 実 PR の取得には GitHub MCP を使う。Step 0 で Continue without を選んでいたら、`claude mcp reset-project-choices` を実行してから `claude` を起動し直し、確認で **Use this MCP server** を選ぶ。環境変数 `GITHUB_PERSONAL_ACCESS_TOKEN` も要る。

- 自動判定と自分の感覚が食い違ったら、**却下基準（CLAUDE.md）の側を調整して再実行する**
- 「基準を直す → 結果が変わる」を1往復すると、このハーネスが**自分の運用に合わせて育てられるもの**だと実感できる
