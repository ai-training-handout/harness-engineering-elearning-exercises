# コスト計測手順（測る → 比べる → 選ぶ）

レビューは4観点を並列に走らせるため、**走らせ方がそのままトークン消費と所要時間に直結する**。ここでは3つの走らせ方を実測し、**速さ・安さ・網羅性のどれを取るかを自分で決める**ところまでを1セットで行う。

> **数値は環境依存である。** モデルと Claude Code のバージョンでトークンとキャッシュの挙動は変わり、同じ条件でも実行ごとに大きくばらつく。
> この手順の目的は「正解の数値を当てる」ことではなく、**自分の環境で測り、自分の予想と比べる**ことにある。

## 計測する3条件

| # | 条件 | 実行方法 | 見るもの |
|---|---|---|---|
| R1 | **4観点 並列**（既定） | `/review sample-pr` | 基準値。**最も速い**（これは環境をまたいで安定している） |
| R2 | **4観点 逐次** | `/review sample-pr --sequential` | 「直列にすれば安くなるはず」という予想が自分の環境で当たるか。**安くなる保証はない** |
| R3 | **Blocker 早期打ち切り** | `/review sample-pr --budget` | Block 確定時に残り観点を実行しない選択。**何を失うか**を確認する（トークンが減るとは限らない） |

## 手順

**先に予想を書く。** 「逐次にしたらトークンは増えるか減るか」「早期打ち切りで減るか」を、実行前に一言ずつ書いてから始める。

各実行のあとに、直近の transcript を集計して記録する。

```sh
python3 cost/measure_tokens.py --label "R1 並列"
python3 cost/measure_tokens.py --label "R2 逐次"
python3 cost/measure_tokens.py --label "R3 早期打ち切り"

python3 cost/measure_tokens.py --report   # 表で比較
```

> 並列で複数の実行を走らせた直後は、`--transcript` で集計対象の transcript を明示したほうが確実（最新ファイルの自動選択が別の実行を掴むことがある）。

**トークンと同時に、検出品質も必ず記録する。**

| 記録項目 | 見る場所 |
|---|---|
| Blocker として何を検出したか（件数と内容） | 指摘一覧 |
| **テストの質**への指摘があったか（形骸テスト・片側しか検証していないテスト） | 指摘一覧 |
| readability の指摘の格付け（実害を言えない指摘が Major 以上になっていないか） | 指摘一覧 |
| 早期打ち切りの場合、未実行の観点が報告に明記されているか | 報告の末尾 |
| 判定 | Approve / Request Changes / Block |

## 数値の読み方（重要）

- **合計トークンの8割強はキャッシュ読み**であり、単価は入力の約1/10。「合計トークン」だけで比較するとコストを過大に見せる。**入力・出力・キャッシュを分けて見る**こと。
- **実行ごとのばらつきは大きい。** 1回の差で「こちらが安い」と結論しない。余裕があれば同じ条件を2回以上回して幅を見る。
- **出力トークンの差は「仕事量の差」**でもある。安くなったのか、仕事が減ったのかを区別する。

## 振り返りの問い（演習で必ず扱う）

1. 並列にして**速くなったのは何で、増えたのは何か**。
2. 逐次は自分の予想どおりだったか。**予想と違ったなら、測らずに決めていたら何を間違えたか**。
3. Blocker 早期打ち切りで**何が得られ、何を失うか**。Block 確定なら残りの観点は不要か、それとも修正を一巡で終わらせるために必要か。
4. **自分の業務ではどれを選ぶか。** 毎日回すとして月にいくらか。速さ・安さ・網羅性のどれを優先するか。

> 4 に唯一の正解はない。**状況によって答えが変わることを理解するのがこのステップの目的**であり、第7部3章「コストと品質・速度のトレードオフ」（コスト最小化ではなく、要求品質を満たす最小コストを狙う）につながる。
