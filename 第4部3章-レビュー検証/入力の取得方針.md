# 入力（PR）の取得方針

レビュー対象として何を渡すかを決める。**渡す情報が少ないほどレビューの土台は薄くなる**ため、必要な範囲を意図して選ぶ。

> **【2026-08-05 実測により記述を修正】** 当初ここには「**見せる範囲を絞ることがコスト制御の第一手**」と書いていたが、**実測は支持しなかった**。差分だけを渡す場合と、変更ファイル全文＋仕様全文を渡す場合を比較しても、消費は **15%しか変わらなかった**（383k → 439k）。対象 PR が diff 821行と小さいためである。
> **大きな PR（数千行規模）で絞り込みが効くかどうかは未検証。** 効くはずだという見込みで教材を組まないこと。詳細：cost/実測結果.md §3。

## 取得するもの / 取得しないもの

| 取得する | 取得しない |
|---|---|
| 変更されたファイルの **diff（変更行とその前後）** | リポジトリ全体・変更のないファイル |
| PR 本文・タイトル・関連 Issue の要約 | Issue のコメント全履歴 |
| 変更に直接関係する仕様の抜粋（`sample-pr/spec-excerpt.md`） | 仕様書の全文 |
| 既存レビューコメント（重複指摘を避けるため） | CI ログの全文（失敗した部分のみ） |

## 取得コマンド

**固定サンプル PR（演習の主対象。GitHub を使わない）**：

```sh
# ローカルの diff をそのまま入力にする
git diff main...feature/task-search -- . > /tmp/pr.diff
```

**実 PR（発展課題。GitHub MCP 経由）**：

```
mcp__github__get_pull_request       # 本文・タイトル
mcp__github__get_pull_request_files # 変更ファイルと patch
```

`get_pull_request_files` は patch（差分）を返すため、ファイル全文の取得（`get_file_contents`）は**原則使わない**。差分だけで判断できない場合に限り、対象ファイルを1つずつ指定して取る。

## 標準（既定）で回す

diff ＋仕様の抜粋を渡す。**この規模の PR では、これ以上絞っても消費はほとんど変わらない**（実測）。

絞り込みの強弱を比較するステップは**演習から外した**。差が出ないうえ、受講生に無駄なトークンを使わせる懸念だけが残るため。コスト比較は「並列／逐次／早期打ち切り」の3条件で行う（[cost/計測手順.md](cost/計測手順.md)）。

## 対象の取り違え防止

PR 番号・リポジトリ名・ブランチの存在確認は、レビュー実行**前**に UserPromptSubmit Hook で機械的に検証する（`.claude/hooks/validate_target.sh`）。取り違えたまま4並列を回すと、間違った対象にコストを払うことになる。
