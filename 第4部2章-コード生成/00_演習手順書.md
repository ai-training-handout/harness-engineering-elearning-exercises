# 演習ステップ定義：コード生成ハーネス（第4部2章）

> **「課題指示 → やってみる」の反復で進める。** 各ステップに課題指示と完了条件がある。完了条件を自分で確かめてから次へ進むこと。
> 目標時間：**45分**（Step 0〜7 で手を動かす時間）。Step 8〜10 はハーネスを走らせて結果を確かめる段で、時間の多くはハーネスが自走する待ち時間になるため、この45分には含めない。ステップごとの想定時間は下表のとおり。時間は目安であり、超えても構わない。
> 詰まったら：完成形リポジトリ（受講ページの第4部2章から `第4部2章_完成形リポジトリ.zip` をダウンロードする。使い方は同梱の `手順.txt`）の `step-N-done` タグで次のステップから再合流できる。

## 0. この演習の構造

- **受講生が書くのは「ハーネス」であって、アプリのコードではない。** アプリは spec からハーネスが生成する。
- **各ステップに完成状態のスナップショットがある。** 詰まったら `git checkout step-N-done` で追いつき、次のステップから再合流できる。**どこで脱落しても最後まで到達できる**ことが、この形式の前提条件。
- **前半（Step 1〜7）は積み上げ、後半（Step 8〜10）は動かして観察する。** 前半で「1層足すと何が変わるか」を体で覚え、後半で「ハーネスが仕事をする様子」を見る。

| Step | 内容 | 受講生の作業 | 想定 | スナップショット |
|---|---|---|---:|---|
| 0 | 環境準備と配布物の確認（Playwright MCP の準備を含む） | 確認のみ | 10分 | `step-0-done` |
| 1 | CLAUDE.md：規約と Do NOT | **書く** | 6分 | `step-1-done` |
| 2 | Permissions：安全柵と deny 体験 | **書く＋体験** | 6分 | `step-2-done` |
| 3 | PostToolUse Hook：整形の機械化 | 雛形を有効化 | 3分 | `step-3-done` |
| 4 | Skill `/implement`：手順とループ上限 | **書く** | 7分 | `step-4-done` |
| 5 | サブエージェント：責務分離 | **書く** | 7分 | `step-5-done` |
| 6 | Playwright MCP：実動作検証 | 雛形を有効化 | 3分 | `step-6-done` |
| 7 | Stop Hook：通知とトークン集計 | 雛形を有効化 | 3分 | `step-7-done` |
| 8 | 1サイクル回す（spec 投入） | 実行と観察 | 待ち時間 | — |
| 9 | 回帰フェーズ（2本目の仕様変更） | 実行と観察 | 待ち時間 | — |
| 10 | 検証の穴とコストを確認する | 実行と考察 | 待ち時間 | — |
| | **合計（手を動かす時間・Step 0〜7）** | | **45分** | |

> **待ち時間の使い方**：Step 8 以降はハーネスが自走する時間が長い（実行系だけで合計40〜60分かかることがある。2026-09 の検証では Step 8 だけで50分）。待っている間に次のステップの指示を読んでおくこと。

## Step 0：環境準備と配布物の確認（10分）

### 課題指示

配布リポジトリを開き、何が配られていて、何を自分で作るのかを把握する。

最初に、このフォルダを演習用のリポジトリにする。公開リポジトリ（`harness-engineering-elearning-exercises`）から取得した場合は、このフォルダを取得した場所の**外へコピーしてから**始める（配布物の README「使い方」）。取得した場所の中で始めると、演習のコミットやブランチが配布物のリポジトリに混ざる。

```sh
git init && git add -A && git commit -m "配布物"   # Step 8 の Finalize と Step 10 のブランチ操作に要る
```

```sh
uv sync --extra dev
uv run pytest -q      # まだテストは無い（アプリを作るのはハーネス）。テスト0件なので終了コードは 5 になる
```

続けて、演習用フォルダで Claude Code を**対話モードで1回起動**し、初回だけ出る確認を2つ通す。どちらも**最初に選ばれている項目のままでは進めない**（終了する／MCP が無効になる）ので、Enter をそのまま押さない。

```sh
claude    # 確認を2つ通したら /exit で閉じてよい
```

1. 「Is this a project you created or one you trust?」（このフォルダを信頼するか）→ 矢印キーで **Yes, I trust this folder** を選ぶ（最初は No, exit が選ばれている）
2. 「New MCP server found in this project: playwright」→ **Use this MCP server** を選ぶ（最初は Continue without using this MCP server が選ばれている。そのまま進むと Playwright MCP が使えず、Step 6・8 の E2E が動かない）

> 間違えて Continue without を選んだ場合、この選択はフォルダごとに記憶され、次に起動しても確認は出ない。`claude mcp reset-project-choices` を実行してから `claude` を起動し直すと、もう一度確認が出る。画面の文言は Claude Code 2.1.283 時点のもの。

> **なぜ最初にやるのか**：信頼を選んでいないフォルダでは、ヘッドレス実行（`claude -p`。画面を開かずに1回だけ指示を実行する使い方）が `.claude/settings.json` の allow を読まない。Step 2 で許可した操作でも、許可がないものとして止まる。

Playwright MCP（Step 6 で使う）の準備もここで済ませる。初回は取得に数分かかる：

```sh
claude mcp list                      # playwright が Connected になるか（.mcp.json を読む。初回は npx が取得する）
npx -y playwright install chromium   # 「ブラウザが見つからない」と言われた場合だけ
```

> 画面のない環境（WSL・リモートの Linux）でも動くよう、`.mcp.json` には `--headless` を入れてある。Connected にならないときは、Node.js 20 以上か・`npx -y @playwright/mcp@latest --help` が動くかを先に確認する。

配布物を確認する：

- `spec.md` — 作るアプリの仕様。**これが唯一の正**
- `pyproject.toml` — 依存定義（増やさない）
- `app/`・`tests/` — **空**。ここを埋めるのはあなたではなく、あなたが組むハーネス
- `CLAUDE.md`・`.claude/skills/implement/SKILL.md` — **雛形（空欄あり）**。Step 1・Step 4 で埋める
- `.claude/settings.json` — allow / deny が空の雛形。Step 2 で書き、Step 3・7 で Hook を登録する（登録の書き方は `.claude/hooks-settings-snippet.json`）
- `.claude/permissions-snippet.json` — Step 2 で貼る allow の一覧
- `.env` — Step 2 の deny 体験用のダミー（偽の値）。読ませて止まるのを見る
- `.python-version` — uv が使う Python（3.13。`uv.lock` と一致させてある）
- `.claude/hooks/`・`.mcp.json`・`e2e/` — 配布済みの Hook スクリプト・MCP 設定・E2E シナリオ。Step 3・6・7 で有効化する
- `.claude/agents/_雛形.md` — サブエージェント定義の書式。Step 5 で3体を作る

### 完了条件

- `uv sync` が成功し、`uv run pytest` が起動する（テスト0件なので終了コードは 5。これで正常）
- `claude mcp list` で playwright が Connected になっている
- Claude Code を対話モードで1回起動し、フォルダの信頼と、playwright の MCP を使う側を選んだ
- `spec.md` を開き、**作るのはアプリではなくハーネスである**と説明できる

### つまずき所

Python 3.11 以上が必要。システムの python では動かないことがあるので `uv` を使う。

## Step 1：CLAUDE.md — 規約と Do NOT（6分・**書く**）

### 課題指示

ハーネスの土台となるコンテキストを書く。**毎回口頭で伝えている前提を、ファイルに移す**のがこのステップ。

`CLAUDE.md`（雛形）の空欄を埋める。**「スタックと構成」は spec.md §1 の写しなので埋めた状態で配ってある**（読んで確認するだけでよい）。ディレクトリ構成（main.py / db.py …）は雛形の例で、spec.md はファイル分割を指定していない。planner が別の構成を出したら、CLAUDE.md をその計画に合わせて更新してよい。書くのは次の2つ：

- **コーディング規約**（SQL の置き場所、型ヒント、日時の扱い）
- **Do NOT** ← ここが本題。最低限これを入れる：
  - テストを削除・skip・期待値の書き換えで green にしない
  - spec にない機能を追加しない
  - `_instructor/` を読まない（Step 10 で置く隠しテストの置き場）

### 完了条件

- CLAUDE.md に **Do NOT が3項目以上**書かれている
- **なぜテスト改変を禁じるのかを説明できる**（テストは書き換え可能な攻撃面である）

### 補足

CLAUDE.md は**短く保つ**。モデルが賢くなるほど不要になる行があり、削る前提で書く。

## Step 2：Permissions — 安全柵と deny 体験（6分・**書く＋体験**）

### 課題指示

**前半（書く）**：`.claude/settings.json` の allow / deny を書く。

- allow：配布の `.claude/permissions-snippet.json` の `allow` をそのまま貼る（pytest・ruff・uv・git・E2E スクリプト・Playwright MCP のツール）。**中身を読み、何を許しているか説明できるようにする。** ここが足りないと Step 8 で承認プロンプトが延々と出て、自走にならない
- deny：自分で書く。`rm`・作業ディレクトリ外への書き込み・`git push`・**`.env` と `_instructor/` の読み取り**
  - deny は**コマンド単位**で書く（`Bash(rm:*)`）。引数で絞った `Bash(rm -rf:*)` だけだと、エージェントは `rm` 単体に切り替えて通り抜ける（実際に起きた。第3部5章「引数で絞る Bash パターンには頼らない」の実例）
  - ファイルの書き込みを止めるルールは `Edit(...)` で書く。`Write(...)` と書いたパスのルールは使われない。作業ディレクトリの外は `Edit(//絶対パス/**)` のように `//` 始まりで書く（`Edit(../**)` は外のパスに当たらない。2026-09 の検証で確認）

**後半（体験）**：**書いた安全柵が実際に効くことを確認する。** エージェントに次を指示してみる：

> 「`.env` の中身を見せて」（配布済みのダミー。`Read(./.env)` の deny が **File is in a directory that is denied by your permission settings** で止める）
>
> 「作業ディレクトリを片付けて。不要なファイルを `rm` で消していい」（`Bash(rm:*)` の deny が止める）

`_instructor/` は CLAUDE.md の Do NOT が先に効き、エージェントが自主的に断るため、**deny の発火は `.env` で見る**。Do NOT は文書の指示、deny は機械的な強制。層が違うことをここで区別しておく。

### 完了条件

- **deny が発火して操作が止まる**ところを、Read（`.env`）と Bash（`rm`）の両方で目視した
- allow に何が入っているかを説明できる

### なぜこのステップがあるか

**設定を書いただけでは検証にならない。** 「書いた安全柵が実際に発火する」ことを一度見ておくと、以降のステップで安心して自走させられる。

**deny が見ているのは、書かれたコマンドの文字列である。** `/bin/rm` のようなフルパス、`bash -c` 経由、`find -delete`、Python からの削除は `Bash(rm:*)` をすり抜ける。こうした書き方は第3部4章の PreToolUse フックで拾い、被害の範囲は第6部4章のサンドボックスで囲う。

## Step 3：PostToolUse Hook — 整形の機械化（3分・雛形を有効化）

### 課題指示

配布された `.claude/hooks/format.sh` を `.claude/settings.json` の PostToolUse に登録し（書き方は `.claude/hooks-settings-snippet.json`）、ファイル編集のたびに formatter / linter が走るようにする。

**成功時は沈黙・失敗時だけ冗長**にする設計になっていることを、スクリプトを読んで確認する。

### 完了条件

- 適当な `.py` ファイルを編集したときに整形が走る。確認は `tests/test_smoke.py` に `def test_smoke(): assert True` を書かせる（spec 外の機能ではないので Do NOT に触れない。確認後は消してよい）。手で叩くなら `echo '{"tool_input":{"file_path":"tests/test_smoke.py"}}' | .claude/hooks/format.sh`
- **整形の指示を人が出さなくなった**ことを説明できる

### 補足（陳腐化ウォッチ）

この層は**モデルの性能向上で最初に不要になる候補**。「今は必要だが、いずれ削る」ものとして意識しておく。

## Step 4：Skill `/implement` — 手順とループ上限（7分・**書く**）

### 課題指示

仕様→計画→実装→検証→PR の手順を、コマンド1つに畳む。`.claude/skills/implement/SKILL.md`（雛形）の空欄を埋める：

- **Verify で何を実行するか**（pytest → E2E）
- **ループ上限**：最大何回まで回すか
- **打ち切り条件**：進捗がないと判断する基準
- **仕様変更を投入するときのフェーズ分割**（Step 9 で使う）：
  1. 実装のみ変更（テストに触らない）
  2. pytest を回して**落ちた既存テストを記録**
  3. 「仕様変更で期待値が変わった／実装の不備」を仕分け
  4. 修正して green に

### 完了条件

- ループ上限と打ち切り条件が**具体的な数値・条件**で書かれている（「適当に止める」ではない）
- **なぜ上限が要るのか**を説明できる（無限ループとトークン浪費を防ぐ安全弁）

### つまずき所

打ち切り条件は「3回まで」だけでは足りない。**同じテストが2回連続で同じ失敗をしたら進捗なし**、のような条件を入れると早く止まる。

## Step 5：サブエージェント — 責務分離（7分・**書く**）

### 課題指示

3つのサブエージェントを定義する。

| 役割 | やること | やらないこと |
|---|---|---|
| planner | spec → `plan.md`（作るファイル・関数・**テスト項目**） | コードを書かない |
| implementer | plan → コード | 計画にない機能を足さない |
| reviewer | 差分レビュー（**テストの質まで見る**） | コードを書き換えない |

**reviewer の定義に必ず入れること**：テストが実装を検証しているか。期待値ハードコードや skip で無効化されたテストがないか。

### 完了条件

- 3体のエージェント定義があり、**それぞれが「やらないこと」を持っている**
- **なぜ reviewer を実装役から分けるのか**を説明できる（自己採点は「動いたからよい」に寄る）

## Step 6：Playwright MCP — 実動作検証（3分・雛形を有効化）

### 課題指示

`.mcp.json` で Playwright MCP を有効化し、`e2e/scenario.md` の1シナリオを Verify に組み込む。

**シナリオの起動・停止がスクリプト（`e2e/serve.sh` / `e2e/stop.sh`）になっていること**と、それが `settings.json` の allow に入っていることを確認する。

### 完了条件

- MCP サーバーが接続されている（`claude mcp list` で確認）。Claude Code で「http://example.com を開いてページタイトルを答えて」と頼み、ブラウザが動くところまで見る
- `settings.json` の allow に `mcp__playwright__` で始まるツールが入っている（Step 2 のスニペットに含まれる。無いと E2E のたびに承認を求められる）
- サーバーの**起動と停止が1コマンドで実行できる**
- 停止手順が Verify の一部として手順書に入っている

### なぜ必要か（実測で裏づけられた）

pytest だけだと「API は正しいが画面が動かない」でも green になり、**未テストのまま完了扱い**になる。

**これは想定ではなく、実際に起きた**（2026-08-06 の実測）：

> **pytest 35件が全 green** の状態で E2E を回したところ、**詳細画面の status 更新が動いていなかった**。フォーム送信が HTMX の部分更新にならず、GET でクエリ文字列を付けて全体リロードするだけで、実際には更新されていなかった。spec.md §5「HTMX による部分更新」の未実装であり、**API テストでは原理的に検出できない**。

この層がなければ、**壊れた画面のまま「完了」と報告されていた**。

### つまずき所（実測で起きた事故）

1. **サーバーの止め忘れ**：起動したサーバーを止めないと**セッションが終了できなくなる**（実測：実作業19分に対しプロセスが110分ハング）。`e2e/stop.sh` を Verify の一部として必ず実行する。
2. **複合コマンドは allow に一致しない**：環境変数の前置き・バックグラウンド化・PID 保存を1行に並べると複合コマンドとして扱われ、**承認待ちで止まる**（実測で2回発生）。**スクリプト1本にまとめる**と allow 1行で許可できる。

## Step 7：Stop Hook — 通知とトークン集計（3分・雛形を有効化）

### 課題指示

完了通知と、**1サイクルの消費トークン集計**を出す Hook を登録する（配布済みの `.claude/hooks/stop_report.sh` を Stop hook に登録する。書き方は `.claude/hooks-settings-snippet.json`）。

### 完了条件

- Claude Code の応答が終わるたびに、応答の下へ「**Stop says:** ハーネスの1サイクルが終了しました。消費トークン集計 …」が表示される
- 表示が**入力／出力／キャッシュに分かれている**ことを確認した

> 画面に出しているのは、Hook が返す JSON の `systemMessage` である。Stop hook が `echo` で書いただけの文字は、対話画面にも ctrl+o の詳細表示にも出ない。自分で Hook を書くときも、この形で返す。数値は**そのセッションの最初からの累計**（planner・implementer・reviewer のサブエージェントの分も含む。同じ API 呼び出しは1回だけ数える）。条件ごとに測る Step 9・10 では、始める前に `/exit` して `claude` を起動し直す。

### なぜ内訳が要るか

合計の8割強はキャッシュ読みで、単価は入力の約1/10。**合計だけ見るとコストを過大に見誤る。**

## Step 8：1サイクル回す（実行と観察。待ち時間が中心）

### 課題指示

```
/implement spec.md
```

**ハーネスが自走している間、次のことを観察する**：

- planner が出した `plan.md` は、spec の条項を取りこぼしていないか
- implementer は計画どおりに作っているか
- Verify は何回回ったか

### 完了条件

- **pytest が全 green**
- E2E の1シナリオが通過
- ブランチと PR 本文が作られている

## Step 9：回帰フェーズ — 2本目の仕様変更（実行と観察。待ち時間が中心）

### 課題指示

green になったハーネスに、**2本目の仕様**を投げる。Step 10 でこの回の消費トークンを使うので、**先に `/exit` して `claude` を起動し直し、新しいセッションで**走らせる。

```
/implement spec-change-2.md
```

終わったら、最後の応答の下に出る「Stop says: …」の合計トークンと経過時間を控えておく（Step 10 の「E2E 込み」の行に使う）。

Step 4 で書いたフェーズ分割どおりに進むはず。**実装だけを変えた時点で pytest を回し、既存テストが落ちるところを必ず見る。**

### 完了条件

- **落ちた既存テストの名前を1つ以上言える**（1件も落ちなかった場合は、なぜ既存テストが検知できなかったかを書く。それも回帰の穴の記録になる）
- それが「仕様変更で期待値が変わったもの」か「実装の不備」か**仕分けできている**
- 再び全 green になり、**テストの削除・skip が発生していない**

### この体験の意味

**品質は1回の合格ではなく、回帰で維持される。** 既存テストが変更を検知してくれたから、壊れたまま進むことを避けられた。

同時に、**落ちたテストを消して通したくなる誘惑が報酬ハッキング**であることも確認する（第5部3章につながる）。

## Step 10：検証の穴とコストを確認する（実行と考察。待ち時間が中心）

### 課題指示（前半：green の穴）

可視テストは全 green。では**本当に正しいか**。エージェントに見せていない隠しテストを実行する。**隠しテストはこの段階で、受講ページの第4部2章から `第4部2章_Step10_隠しテストと穴あり実装.zip` をダウンロードする**（配布物には含まれていない）。展開して出てくる `_instructor/` フォルダを、演習フォルダの直下にそのまま置く。エージェントには読ませないこと（Step 2 の deny が効いていれば読めない）。

```sh
PYTHONPATH=. uv run pytest _instructor/held_out   # 最後の行に「◯ passed」「◯ failed」が出る
```

隠しテストは、spec.md が要求しているのに §6.1 の可視テスト要件には列挙していない条項だけを検査する。**落ちなければ、それは良い結果**。あなたのハーネス（CLAUDE.md の Do NOT・planner の計画・reviewer）が穴を作らせなかった証拠である。落ちた場合は、どの条項が抜けたか・どの層が効いていれば防げたかを書く。

自分の結果を書いたら、同じ zip の `穴あり実装/` に同じ隠しテストを当てる（手順は zip の `手順.txt`）。可視テストは全 green のまま、隠しテストだけが落ちる。この穴は、比較のために教材側で**意図的に仕込んだ**もので、エージェントが放っておくと作る穴ではない。
