# E2E シナリオ（Playwright MCP で実行する）

> `spec.md` §6.2 の1シナリオ。Verify ステップで pytest が green になったあとに実行する。
> 実装コードではなく**操作手順**として書く。ハーネスは Playwright MCP でブラウザを実際に操作し、各確認項目を満たすことを確かめる。

## 事前準備

```sh
./e2e/serve.sh
```

> **スクリプト1本にしてある理由**：環境変数の前置き・バックグラウンド化・PID 保存を1行に並べると**複合コマンド**として扱われ、Permissions の allow に一致せず**承認待ちで止まる**（実測で2回発生）。単一コマンドにすることで allow 1行で許可できる。

ベース URL：`http://127.0.0.1:8765`

## 後片付け（**必須。省略しない**）

シナリオが終わったら、**必ずサーバーを停止する**。

```sh
./e2e/stop.sh
```

> **なぜ必須か**：停止し忘れると、起動したプロセスが標準出力を掴んだままになり **Claude Code のセッションが終了できなくなる**（実測：実作業19分に対しプロセスが110分ハングした）。次の実行もポート衝突で失敗する。**E2E を回したら必ず落とす**、をハーネスの手順として持つこと。

## 手順と確認項目

| # | 操作 | 確認すること |
|---|---|---|
| 1 | `/login` を開き、`name` に `member1` を入力して送信 | `/tasks` に遷移する。ログイン中のユーザー名が表示される |
| 2 | 一覧上部の新規作成フォームでタイトルを入力して作成 | **ページ全体がリロードされずに**（HTMX の部分更新）一覧に新しいタスクが現れる |
| 3 | 作成したタスクの詳細（`/tasks/{id}`）を開く | タイトル・status・priority・期限・担当者・タグが表示される |
| 4 | 詳細で status を `doing` に変更して保存 | 部分更新で status の表示が `doing` に変わる |
| 5 | 一覧に戻る | 当該タスクの status が `doing` になっている |
| 6 | ログアウトする | `/login` に遷移する。この状態で `/tasks` を開くと `/login` にリダイレクトされる |

## 失敗時の扱い

E2E が落ちた場合も、pytest の失敗と同様に**実装側を修正**して再実行する。シナリオを緩めて通すことは禁止。

## なぜ E2E を入れるか（設計意図）

pytest だけだと「API は正しいが画面が動かない」状態でも green になり、**未テストのまま完了扱い**になりうる。HTMX の部分更新は API テストでは検証できないため、実ブラウザでの確認をループに組み込んでいる。
